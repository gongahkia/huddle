# Portable host transfers

`ReviewStore` implements JSON/Markdown export and the four v2 import operations on SQLite, PostgreSQL, MySQL and transaction-capable MongoDB. The host supplies its existing authorization callback and storage. No Huddle product server, mandatory worker, source URL fetch or account creation is involved. Mount the existing [HTTP bridges](host-http.md) or call the adapter methods directly.

Exports authorize every selected environment before returning a download. Iteration opens one consistent backend snapshot, validates counts/references/summaries and streams with a one-record window and backpressure. JSON includes every selected thread, comment and history entry; Markdown escapes user text. The final completeness footer is released only after the snapshot succeeds. Cancellation, revocation, timeouts and backend failure end the stream without a successful completeness marker. Consumers must validate the complete JSON; a partially downloaded file is not a backup. Full workspace export requires the host to enumerate all authorized environments explicitly.

## Import and resume

1. Call `stageImport(scope, chunks, signal)` with UTF-8 JSON bytes. The host stores 64 KiB chunks and seals a manifest only after complete structural and semantic validation. The returned digest is SHA-256 of the exact bytes. No discussion records are written by staging or preview.
2. Call `previewImport(scope, {uploadId, digest, mapping}, signal)`. Inspect counts, historical authors and conflicts before deliberately executing. The destination workspace comes from `scope`; source environments are retained unless explicitly mapped. Origin mappings use exact HTTP(S) origins without credentials or paths. Absolute page keys matching that origin also change; paths remain unchanged. URL parsing may percent-encode Unicode when an origin is remapped. Identity mapping accepts existing host-approved directory IDs only, across every mapped environment.
3. Deliberately call `executeImport(scope, {previewId, digest, idempotencyKey}, signal)`. Each acknowledged POST commits at most one configured record batch within one environment. Continue acknowledged batches using **the same** request key until the result is complete or failed. A GET of `importProgress` is read-only and never advances work. No background worker is required. After an uncertain response, inspect progress and explicitly resume with the original key. Do not automatically replay uncertain mutations.
4. Complete requires exact expected/processed counts. A conflict returns a failed job with exact rejected record IDs; already acknowledged records remain. A transient database/transport failure leaves durable progress resumable. Expired staging requires uploading and previewing again; permanent provenance receipts still protect previously published discussion from duplication or overwrite.

Upload, preview and job access is actor-bound, scoped and expiring. Every operation rechecks authorization, including all destination environments, progress and export streaming. Execution is bound to preview, digest, mapping and request key. Changing that binding is a conflict. Revocation denies subsequent batches and progress reads.

Imports use deterministic destination IDs derived from source dataset, collection, source ID and destination scope; a native same-dataset/same-scope round trip can retain its IDs. Unrelated incoming/destination ID collisions are reported, not overwritten. Comment/history references and known reply-history comment IDs follow destination IDs. Opaque history data and view context remain unchanged. Threads publish only after all their planned children have been accounted for; incomplete child batches are hidden from public list/detail/export reads. Repeating a file accounts for matching provenance without overwriting later replies, status changes or assignments. Imports do not merge changed versions of already imported source records: conflicting content or mapping is reported explicitly.

Latest-comment summaries are recomputed by creation instant and actual destination ID. When multiple comments share the exact creation instant, remapping IDs can change which tied comment appears in that derived summary; all comments and original timestamps/IDs remain preserved.

`provenance` retains immediate source dataset/record/digest and a flat `previous` chain. Thread provenance includes original scope, page key and URL; attribution provenance includes the historical ID/name, including when explicitly mapped. Unmatched mentions and assignees remain historical metadata. They do not become live directory matches, notification targets or authorization grants. Historical identity mapping never changes the host login or access policy.

## Limits and explicit cleanup

The optional fourth `ReviewStore` constructor argument is `TransferOptions`: `limits` (maxBytes, maxRecords, maxDepth), `batchSize`, `ttlMs`, and `timeoutMs`. Defaults are 32 MiB, 100,000 combined records, depth 32, 100 records per batch, 24 hours staging lifetime, and 120 seconds per direct SDK transfer operation. Records have a 10,000-node complexity bound. Supported configurable maxima are 64 MiB, 1,000,000 records, depth 64, 1,000 records per batch, 30 days and one hour respectively. The HTTP bridge additionally defaults to a 32 MiB upload limit and a 15-second request deadline; configure host/proxy/client deadlines together. A limit or deadline failure is visible and does not establish completion.

Parsing/preview hold one configured-size file plus its bounded normalized plan in memory; this is not a constant-memory import parser. Upload chunk documents remain below MongoDB's document limit. Import requests perform no unbounded database write transaction: batch progress, records and receipts commit together. Large source threads can span requests while their header remains unpublished. A slow deployment can reduce the batch size or implement a host-managed job behind its adapter.

Call `store.cleanupImports(scope, signal, limit)` deliberately, in a host CLI or host-owned maintenance task. The default limit is 100, maximum 1,000. Repeat until both returned counts are zero. Cleanup acts only on the current authorized actor's expired staging in that scope; it is not an account-wide administrator sweep. Clean every destination environment used by imports as well as the upload scope. It removes expired upload chunks/manifests, previews, jobs and unpublished import children. Published children are retained and their expired staging metadata is cleared. Native review rows, threads, events, provenance receipts and subsequent activity are not deletion targets. Package uninstall never calls cleanup or deletes the database. Keep original files and verified backups outside runtime staging and Git.

`pnpm test:storage` runs the shared real-backend conformance suites and all sixteen ordered database transfer pairs; `pnpm test:portability` runs only those pairs. The portability fixture has 108 threads, 368 comments (261 on one thread), 109 history entries including resolution history, two environments, open/resolved status, historical attribution, prior provenance, optional coordination fields, Unicode and malicious-looking plain text. The twelve packed server/database combinations exercise positive HTTP transfers separately through `pnpm test:matrix`. Browser transfer UI, final resource/performance evidence, Pronto migration and hosted acceptance are later gates.
